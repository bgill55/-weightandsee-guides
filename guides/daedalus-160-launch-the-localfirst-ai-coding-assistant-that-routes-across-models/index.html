Daedalus 1.6.0 Launch: The Local‑First AI Coding Assistant That Routes Across Models

This guide walks through the complete setup and usage of Daedalus 1.6.0, a standalone terminal-based AI coding assistant that intelligently routes requests across local and cloud LLM providers. You'll learn how to install it, configure local and remote model connections, and use the multi-agent orchestrator to break complex coding goals into tracked, parallelized tasks.

🎯 Key Takeaways

  • 1Daedalus 1.6.0 unifies local and cloud LLM usage by intelligently routing requests across LM Studio, Ollama, llama.cpp, vLLM, OpenAI, Groq, OpenRouter, and Anthropic based on model health and task suitability.
  • 2The multi-agent orchestrator decomposes high-level goals into parallel tasks handled by five specialized sub-agents: Planner, Coder, Researcher, Reviewer, and Debugger, each with distinct responsibilities.
  • 3Automatic health checks every 30 seconds route requests away from models that are unresponsive, unloaded, or saturated with context, eliminating manual provider switching.
  • 4Installation is a single npm command, and first-run auto-detects local LLM servers on your machine, falling back to remote provider prompts if none are found.
  • 5Configuration is fully transparent and user-editable via ~/.daedalus/config.json, giving you full control over provider endpoints, model selection, and routing preferences.
  • 6Daedalus provides terminal-native agent access to your actual file system, git history, shell, web search, and codebase indexing — not a chatbot guessing at your project structure.
  • 7Failed tasks pause the orchestrator and present four options — retry, edit, skip, or abort — keeping the developer in full control at all times.

📋 Prerequisites

  • Node.js (v18 or later) and npm installed on your machine
  • At least one accessible LLM provider — either a local server (LM Studio, Ollama, llama.cpp, or vLLM) or a remote API key (OpenAI, Groq, OpenRouter, or Anthropic)
  • A terminal environment (macOS Terminal, Windows Terminal, Linux shell, or any terminal emulator)
  • Familiarity with basic CLI navigation and configuration file editing
  • A codebase or project directory where you want the agent to operate

📝 Step-by-Step Guide

1

Step 1: Install Daedalus CLI Globally

Install Daedalus from npm with a single command. This makes the `daedalus` command available system-wide in your terminal. Ensure you have Node.js v18+ and npm installed before running this step.

npm install -g daedalus-cli
2

Step 2: Launch Daedalus and Run the First-Time Configuration Wizard

Run the `daedalus` command with no arguments. On first launch, Daedalus automatically scans your machine for running local LLM servers (LM Studio on port 1234, Ollama on port 11434, llama.cpp, vLLM, etc.). If local servers are detected, it lists them and prompts you to confirm or add additional endpoints. If no local servers are found, it walks you through entering a remote provider API key (OpenAI, Groq, OpenRouter, or Anthropic). All configuration is written to ~/.daedalus/config.json.

daedalus

# Example first-run output:
# [Daedalus] Scanning for local LLM servers...
# [Daedalus] Found Ollama at http://localhost:11434
# [Daedalus] Found LM Studio at http://localhost:1234
# [Daedalus] No remote providers configured.
# [Daedalus] Add a remote provider? (y/n): y
# [Daedalus] Select provider: [1] OpenAI  [2] Groq  [3] OpenRouter  [4] Anthropic
# [Daedalus] Enter API key: sk-...
# [Daedalus] Configuration saved to ~/.daedalus/config.json
3

Step 3: Review and Customize Your Configuration File

Open ~/.daedalus/config.json in your preferred editor. This file contains all provider endpoints, API keys, default models, health check intervals, and routing preferences. You can manually add or remove providers, set model-specific context windows, configure priority routing order, and define fallback chains. No setting is hidden — everything is editable and transparent.

{
  "providers": [
    {
      "name": "ollama-local",
      "type": "local",
      "baseUrl": "http://localhost:11434",
      "models": ["codellama:13b", "llama3:70b"],
      "priority": 1,
      "contextWindow": 8192
    },
    {
      "name": "openai-cloud",
      "type": "remote",
      "baseUrl": "https://api.openai.com/v1",
      "apiKey": "sk-...",
      "models": ["gpt-4o", "o1"],
      "priority": 2,
      "contextWindow": 128000
    }
  ],
  "healthCheckIntervalMs": 30000,
  "routingStrategy": "smart",
  "maxRetries": 2,
  "agentTools": ["filesystem", "terminal", "git", "websearch", "codeIndex"]
}
4

Step 4: Start a Multi-Agent Orchestration Session

Navigate to your project directory and run `daedalus`. Enter a high-level goal when prompted. The orchestrator activates the Planner sub-agent, which decomposes your goal into discrete tasks with verification criteria. Each task is then assigned to the appropriate specialized sub-agent: Coder handles file edits and command execution, Researcher searches the codebase and web, Reviewer checks security and formatting, and Debugger runs tests and parses error logs. A live checklist tracks progress in real time.

cd ~/my-project
daedalus

# Enter your goal when prompted:
# > Refactor the authentication module to use JWT tokens and add comprehensive test coverage

# The orchestrator responds:
# [Planner] Goal accepted. Decomposing into tasks...

#   ✅ Task 4: Implement token validation middleware   (→ Coder)
#   ✅ Task 5: Add unit tests for token functions     (→ Coder)
#   ✅ Task 6: Add integration tests for auth flow    (→ Coder)

#   ✅ Task 8: Run full test suite and fix failures   (→ Debugger)

Step 5: Handle Task Failures and Control the Agent

If any task fails, exceeds its turn limit, or produces unexpected output, the orchestrator pauses and presents the failed task along with four options: retry (re-run the same task, optionally with more context), edit (modify the task description or constraints before retrying), skip (mark the task done and move on), or abort (stop the entire orchestration). This prevents runaway agent behavior and keeps you in control. You can also interrupt at any point with Ctrl+C.

# When a task fails, Daedalus responds:
# [Orchestrator] ⚠️  Task 4 failed: Token validation middleware
#   Error: Test suite failed — 3 assertions in auth_middleware.test.js
#   Turn limit reached: 15/15
#

#   [3] Skip task

# [Orchestrator] Retrying Task 4 with updated description...

Step 6: Configure Intelligent Routing Between Local and Cloud Providers

Daedalus performs health checks on all configured providers every 30 seconds. It tracks which models are loaded, responsive, and have available context capacity. For quick tasks (formatting, simple lookups), it prefers local models for speed and privacy. For complex reasoning tasks, it escalates to cloud providers. You can customize routing behavior in config.json by setting per-provider priority, per-task-type routing rules, and context-window-aware model selection.

# ~/.daedalus/config.json — routing configuration
{
  "routing": {
    "strategy": "smart",
    "healthCheckIntervalMs": 30000,
    "taskRoutingRules": {
      "codeGeneration": { "prefer": "cloud", "fallback": "local" },
      "codeSearch": { "prefer": "local" },
      "testExecution": { "prefer": "local" },
      "securityReview": { "prefer": "cloud", "model": "gpt-4o" }
    },
    "contextOverflowAction": "escalate",
    "localPrivacyPatterns": ["**/secret*", "**/*.env", "**/credentials*"]
  }
}

💡 Pro Tips

Pro Tip: Run Ollama or LM Studio with your most-used model pre-loaded before launching Daedalus — the health check will detect it immediately and prioritize it for low-latency tasks.
Pro Tip: Set the `localPrivacyPatterns` config to route any tasks touching sensitive files (secrets, credentials, .env) exclusively to local providers.
Pro Tip: Use the `--provider` flag on launch (e.g., `daedalus --provider ollama-local`) to force a single-provider session when you want guaranteed local-only execution.
Pro Tip: The Researcher agent has web search enabled by default — use it to have Daedalus pull in documentation or Stack Overflow answers relevant to your codebase in real time.
Pro Tip: Pin a specific model for the Reviewer agent by setting `"securityReview": {"model": "gpt-4o"}` in your routing config — security reviews benefit from the strongest reasoning model available.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Not pre-loading local models — If Ollama or LM Studio is running but no model is loaded into memory, Daedalus' health check will mark the provider as unavailable. Pre-load your model before starting a session.
Watch Out: Pitfall 2: Incorrect context window settings — If `contextWindow` in config.json exceeds the actual model's capacity, requests will fail silently or return truncated responses. Always verify against your model's documented limit.
Watch Out: Pitfall 3: Forgetting to set the working directory — Daedalus operates relative to your current shell directory. If you launch it from the wrong folder, the Researcher and Coder agents won't find your project files. Always `cd` into your project root first.
Watch Out: Pitfall 4: API key exposure — Your config.json stores API keys in plain text. Ensure file permissions are restricted (`chmod 600 ~/.daedalus/config.json`) and never commit this file to version control.
Watch Out: Pitfall 5: Overloading the orchestrator with vague goals — Goals like 'improve the codebase' are too broad and will cause the Planner to generate an excessive number of tasks. Be specific: 'Add input validation to the user registration endpoint and write tests for it.'

❓ Frequently Asked Questions

Can I use Daedalus entirely offline with no cloud providers?

Yes. Configure only local providers (Ollama, LM Studio, llama.cpp, or vLLM) in ~/.daedalus/config.json. Daedalus will route all tasks to your local models. Just ensure your models are pre-loaded and responsive before starting a session.

How does Daedalus decide which model to route a request to?

Daedalus runs health checks every 30 seconds and tracks model responsiveness, load status, and available context capacity. For simple tasks, it prefers local models for speed and privacy. For complex reasoning, it escalates to cloud providers. You can customize this behavior with per-task-type routing rules in config.json.

What happens if all configured providers are down or unreachable?

If every provider fails its health check, Daedalus pauses and notifies you in the terminal. It will not silently fail or produce hallucinated results. You can restart providers and resume, or switch configuration with the --provider flag.

Can I add my own custom sub-agents to the orchestrator?

The current 1.6.0 release ships with five fixed sub-agents (Planner, Coder, Researcher, Reviewer, Debugger). Custom sub-agents are planned for a future release. For now, you can influence behavior by writing detailed task descriptions and adjusting routing rules in config.json.

Is my code sent to cloud providers when using remote LLMs?

Yes — when a task is routed to a remote provider, the relevant code context is sent to that provider's API. Use the `localPrivacyPatterns` config option to ensure sensitive files and secrets are only processed by local models. Daedalus logs which provider handled each task in the session transcript.

How do I update Daedalus when a new version is released?

Run `npm install -g daedalus-cli` again to pull the latest version. Your existing ~/.daedalus/config.json is preserved across updates. Check the GitHub releases page for breaking changes before updating.
