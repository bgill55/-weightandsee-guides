Daedalus Windows Crash Fix: How v3.13.3 Restores Autonomous Build‑Fix Loops

This deep‑dive examines the rapid Windows stability updates in Daedalus v3.13.1‑v3.13.3, focusing on the crash‑fix that eliminates the 0xC0000142 error, the false‑revert prevention for valid edits, and the new routing floor that keeps build‑fix tasks on a high‑tier model. By dissecting the underlying problems and the patches applied, we see how Daedalus now enables uninterrupted autonomous coding loops on Windows platforms.

🔬 Key Findings

Crash Fix Eliminates 0xC0000142 Termination

The original crash stemmed from child processes inheriting the parent’s stdio. When the parent’s stdin pipe closed, the entire process group terminated, yielding exit code 3221225794 (0xC0000142). The fix rewrites `src/tools/builtin/terminal.ts` to ignore stdin, pipe stdout/stderr, and detach children into their own process groups, preventing Ctrl‑C from killing downstream `tsc` compilations.

False‑Revert Prevention Preserves Valid Edits

Previously, Daedalus would revert a patch if a pre‑existing type error in the file was mistakenly flagged as newly introduced after the edit. The new logic creates a temporary baseline before applying edits and diffs only newly generated diagnostics, ensuring legitimate changes survive even in noisy codebases.

Routing Floor Keeps Build‑Fix Tasks on High‑Tier Models

Without a routing floor, the router could downgrade tasks to a lower‑capability model (e.g., `freellmapi‑cf‑meta‑llama‑4‑scout‑17b`) after a few trivial turns, leading to hallucinated tool names and missed build‑related keywords. The floor forces any turn containing keywords like `build`, `tsc`, `type‑error`, or `refactor` to stay on models with at least 120 B parameters (e.g., `gpt‑oss‑120b`).

Combined Patches Yield Zero Crashes in Real‑World Benchmarks

Testing on the `prompt‑vault` project showed a dramatic shift: prior to the updates, the autonomous agent stalled after five crashes; after applying v3.13.3, the agent experienced zero crashes, maintained continuous use of the 120 B model, automatically recovered from bad patches, and compiled the project with zero diagnostics.

Simple Upgrade Path Enables Immediate Benefits

Users can adopt all three fixes instantly via a single npm command (`npm install -g daedalus-cli`) followed by `daedalus-cli start` in their project directory, requiring no manual code changes.

⚙️ Technical Background

Daedalus is an autonomous coding agent that orchestrates child processes (e.g., TypeScript compilation) to iteratively refactor code. On Windows, process termination semantics differ from Unix, especially regarding inherited stdio handles and signal propagation. Additionally, Daedalus relies on a routing layer that selects large language models based on task complexity, and it uses diagnostic diffing to decide whether a patch should be kept or reverted.

❓ Frequently Asked Questions

How do I upgrade to the crash‑fix version?

Run `npm install -g daedalus-cli` to install the latest CLI, then execute `daedalus-cli start` inside your project directory.

Will the fixes work on macOS or Linux?

The stdio‑inheritance fix is Windows‑specific; the false‑revert and routing floor improvements are cross‑platform and will apply on all OSes.

Do the patches increase resource usage?

The routing floor may keep the agent on larger models (≥120 B), which can raise GPU/CPU usage and cost. The other fixes have negligible performance impact.

How can I verify that the crash‑fix is active?

After upgrading, run a build‑fix loop that previously triggered the 0xC0000142 error. If the process no longer terminates and logs show the detached child process, the fix is in effect.

Can I customize the routing floor keywords?

Yes. The routing configuration (`routing.json`) contains a `keep_on_intelligence_keywords` array; you can add or remove keywords to control model selection for specific tasks.
