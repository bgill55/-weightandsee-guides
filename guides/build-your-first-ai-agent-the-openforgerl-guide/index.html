Step 1: Define the Environment Interface

Wrap your target application (e.g., a web scraper or CLI tool) in a Python class. This class must expose a `step` function that accepts an action and returns the resulting state, such as data or an error message. This ensures the agent interacts with the environment within a Markov Decision Process.

class CustomEnvironment:
    def __init__(self, app_interface):
        self.app = app_interface

    def step(self, action):
        try:
            result = self.app.execute(action)
            return result, 0  # state, default_reward
        except Exception as e:
            return str(e), -1  # error state, penalty
2

Step 2: Configure State and Action Spaces

In your configuration file, specify the state space as the context window of the LLM and define a discrete action space. Limiting the action space to specific valid tokens or Python function calls prevents the agent from attempting hallucinated or invalid APIs.

env_config = {
    "state_space": "llama_context_window",
    "action_space": {
        "type": "discrete",
        "valid_actions": ["query_sql", "read_file", "summarize_text"]
    }
}

Step 3: Implement the Reward Function Logic

Encode your business logic into the reward function by setting binary flags for task completion and penalizing steps that result in exceptions. For text generation tasks, use a cosine similarity check against a ground truth summary to prevent the agent from 'cheating' with empty outputs.

def calculate_reward(action, result, objective):
    if "error" in result.lower():
        return -1.0
    
    if objective == "summarize":
        similarity = cosine_similarity(result, ground_truth)
        if similarity > 0.8 and 50 < len(result) < 200:
            return 1.0
    return 0.0
4

Step 4: Configure Policy and Reward Models

Set up Llama 4 as your primary policy network for handling complex instruction following. Configure DeepSeek-V4 as the secondary model to evaluate outcomes and assign scalar reward values based on your objective function.

model_config = {
    "policy_model": {
        "name": "Llama-4-405B",
        "role": "actor",
        "latency_optimization": True
    },
    "reward_model": {
        "name": "DeepSeek-V4",
        "role": "critic"
    }
}
5

Step 5: Initialize and Run the Training Loop

Instantiate the OpenForgeRL trainer class with your models and environment configuration. The framework handles rollouts, experience collection, and Proximal Policy Optimization (PPO) to update the Llama 4 weights, favoring successful strategies over time.

from openforgerl import Trainer

trainer = Trainer(
    policy_model=model_config["policy_model"],
    reward_model=model_config["reward_model"],
    env_config=env_config
)

# Start training loop
trainer.train(episodes=500)

💡 Pro Tips

Pro Tip: Use a discrete action space restricted to specific Python function names to drastically reduce API hallucinations.
Pro Tip: When using Llama 4, ensure your hardware setup utilizes NVLink for the 405B parameter variant to maximize throughput.
Pro Tip: Incorporate a 'refusal message' penalty in your reward function to discourage the agent from giving up on tasks.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Failing to strictly wrap the environment in a class, leading to unstructured state data the LLM cannot process.
Watch Out: Pitfall 2: Using vague goals in the reward function (e.g., 'be helpful'), which results in unpredictable agent behavior.
Watch Out: Pitfall 3: Ignoring latency; if the reward model (DeepSeek-V4) is too slow, the training loop will become unresponsive.

❓ Frequently Asked Questions

Why use DeepSeek-V4 instead of other models for the reward model?

DeepSeek-V4 processes state-action pairs significantly faster than previous iterations, ensuring the training loop remains tight and responsive.

What is the benefit of separating the actor (policy) from the critic (reward model)?

This separation allows the agent to explore actions while a secondary objective model evaluates the outcome, preventing the agent from getting stuck in local optima or repetitive safe actions.

How does OpenForgeRL prevent agents from repeating the same error?

It treats agent interaction as a Markov Decision Process where errors result in negative reward signals, which propagate back through the network to update the agent's internal policy via PPO.
