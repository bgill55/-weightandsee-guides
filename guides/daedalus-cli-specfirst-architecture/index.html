Daedalus CLI SpecFirst Architecture

This guide walks you through using Daedalus CLI's SpecFirst Architecture to define a CLI via a YAML spec, generate type‑safe TypeScript code, keep sub‑agents in sync, validate runtime arguments, and automatically produce documentation and a UI. By following the steps you’ll see how the spec becomes the single source of truth for the whole stack.

🎯 Key Takeaways

  • 1A YAML spec is the authoritative contract for commands, options, and validation rules.
  • 2`daedalus generate` creates fully typed TypeScript modules—no manual parser needed.
  • 3Sub‑agents are kept in sync automatically; the tool overwrites drifted files on `daedalus sync`.
  • 4Runtime validation happens against a generated JSON contract, providing instant, user‑friendly error messages.
  • 5Daedalus can auto‑heal spec‑drift, roll back changes, and generate synchronized React UI and docs.
  • 6The test harness derived from the spec ensures edge‑case coverage before code is shipped.
  • 7Documentation and UI are regenerated on‑the‑fly via hot‑module replacement, keeping everything up‑to‑date.

📋 Prerequisites

  • Node.js (>=14) and npm installed
  • TypeScript compiler (`npm install -g typescript`)
  • Git for version control
  • Basic familiarity with YAML and CLI usage

📝 Step-by-Step Guide

1

Step 1: Create the Spec File

Open your favorite IDE and create a `spec.yaml` file that defines each command, its description, options, and validation rules. Use camelCase for option names and include enum definitions where appropriate. This file will be the single source of truth for the CLI, UI, and documentation.

```yaml
# spec.yaml
commands:
  generate-spec:
    description: "Generate markdown and JSON contract"
    options:
      - name: output
        type: string
        required: true
        description: "Path to write the generated files"
      - name: format
        type: enum
        enum: [markdown, json]
        default: markdown
        description: "Output format"
```
2

Step 2: Generate Typed Code

Run the Daedalus generator to turn the YAML spec into TypeScript modules. The command reads `spec.yaml`, emits a command dispatcher, validation schemas, and typed wrappers, and places them under `src/generated`. No hand‑written parsing is required; the generated code mirrors the spec exactly.

```bash
# Install Daedalus CLI globally if you haven't already
npm install -g @daedalus/cli

# Generate the code
daedalus generate --spec ./spec.yaml --out ./src/generated
```
3

Step 3: Keep Sub‑Agents Synchronized

Each sub‑agent (e.g., `api`, `auth`) has a watcher that regenerates its file whenever the spec changes. After editing the spec, run `daedalus sync` to update all generated modules. If you manually edit a generated file, the next sync will overwrite it, preserving spec fidelity.

```bash
# After modifying spec.yaml
# Re‑generate all sub‑agent files

daedalus sync --spec ./spec.yaml
```
4

Step 4: Execute a CLI Command with Validation

Run a command defined in the spec. Daedalus validates arguments against the generated JSON contract before invoking any business logic. Invalid flags are rejected instantly with a colored error summary that points to the correct usage.

```bash
# Run the generate‑spec command

daedalus run generate-spec --output ./dist/spec.md --format markdown

# Example of an invalid flag

daedalus run generate-spec --unknownFlag
# Output:
# ❌ Error: Unknown flag '--unknownFlag'.
#   Did you mean '--output'?
#   See spec for full list of options.
```
5

Step 5: Generate Documentation and UI

Produce a static documentation site and a React‑based UI that consumes the same JSON contract. The `doc-gen` command reads the spec, creates Markdown, then converts it to HTML. Hot‑module replacement ensures UI updates without a full page reload when the spec changes.

```bash
# Generate docs

daedalus doc-gen --spec ./spec.yaml --out ./docs

# Start the UI with hot‑module replacement

daedalus ui --watch
```
6

Step 6: Use Self‑Healing and Rollback (Optional)

If Daedalus detects drift (e.g., missing files or checksum mismatches), it auto‑generates a corrective diff and writes a backup. You can revert unintended changes with `daedalus rollback`.

```bash
# Trigger self‑healing (usually automatic on sync)

daedalus sync --spec ./spec.yaml

# If needed, rollback the last auto‑correction

daedalus rollback --backup .daedalus.backup
```

💡 Pro Tips

Pro Tip: Add a `.daedalusrc` file to configure thresholds for self‑healing, e.g., `{ "healThreshold": "low" }`.
Pro Tip: Run `daedalus test --spec ./spec.yaml` to execute the generated test harness and catch edge‑case failures early.
Pro Tip: Enable HMR in the UI by passing `--hmr` to `daedalus ui` for instant component updates without a page refresh.

⚠️ Common Pitfalls

Watch Out: Editing generated TypeScript files directly – these changes will be overwritten on the next sync.
Watch Out: Forgetting to commit the updated `spec.yaml` before CI runs – the CI pipeline will regenerate stale code.
Watch Out: Misconfiguring `.daedalusrc` and disabling self‑healing unintentionally, leading to spec drift.

❓ Frequently Asked Questions

Do I need to write any parsing code after generating the spec?

No. `daedalus generate` emits a complete parser and typed wrappers that respect the spec, so you never write manual argument parsing.

Can I customize error messages shown when a flag is invalid?

Yes. In `spec.yaml` you can add an `errorMessage` field to each option, and Daedalus will use it when generating validation schemas.

What happens if I accidentally edit a generated file?

The next `daedalus sync` will overwrite the change, preserving spec fidelity. A backup is saved in `.daedalus.backup` in case you need to restore it.

How does the UI stay in sync with the spec without a full reload?

The UI watches the generated JSON contract. When the spec changes, Daedalus rebuilds the component tree and pushes a hot‑module replacement update, injecting new fields on the fly.

Is there a way to disable the self‑healing feature for certain modules?

Yes. In `.daedalusrc` you can list sub‑agents under `disableHealing: [ "auth", "metrics" ]` to turn off auto‑correction for those modules.
