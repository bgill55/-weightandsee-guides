Weight and See Open-Source AI Hub

This guide walks you through setting up the Weight and See Open‑Source AI Hub, spinning up its micro‑services stack with Docker Compose, verifying the system health, and interacting with the hub via the `wsctl` CLI and MetaVision API. It also covers how to run benchmark suites and explore the security sandboxing and message‑bus architecture.

🎯 Key Takeaways

  • 1The hub is deployed as a set of Docker containers that include a model registry, sandboxed inference engine, and a UI gateway.
  • 2Health checks are exposed via `curl localhost:8080/health` and return a JSON payload confirming readiness.
  • 3The `wsctl` CLI offers commands to list models, run benchmarks, and launch vision pipelines in a single command.
  • 4MetaVision provides REST endpoints (`/detect`, `/segment`, `/caption`) for vision tasks and can be chained with the hub’s inference engine.
  • 5Security is enforced by gVisor sandboxes and a NATS message‑bus that decouples components and isolates failures.
  • 6Rust‑based plugins register model metadata into a central catalog, enabling the benchmark engine to spin up temporary containers.
  • 7The hub’s architecture allows for easy addition of new models or agents via the plugin system and the `OneCLI` agent framework.

  • Git 2.x or higher
  • Docker Engine 20.x+ with Docker Compose
  • Basic familiarity with command‑line interfaces and JSON
  • Optional: Rust compiler for building plugins (if you plan to extend the catalog)

📝 Step-by-Step Guide

1

Step 1: Clone the Weight and See AI Hub Repository

Open a terminal and clone the repository to a local directory. This pulls all the source code, Docker Compose files, and documentation needed to run the hub.

git clone https://github.com/weightandsee/ai-hub.git && cd ai-hub
2

Step 2: Spin Up the Docker Compose Stack

Use Docker Compose to start all micro‑services in detached mode. The compose file defines the model registry, sandboxed inference engine, UI gateway, and NATS bus. Ensure you have enough RAM (at least 4 GB) for the containers.

docker compose up -d
3

Step 3: Verify Service Health

Once all containers report healthy status, check the hub’s health endpoint. A successful call returns a JSON object indicating each component’s status.

curl http://localhost:8080/health
4

Step 4: Interact with the Hub Using wsctl

The `wsctl` CLI is bundled with the hub. It lets you list available models, run benchmark suites, and launch vision pipelines. You can also edit the local model catalog.

wsctl list models
wsctl benchmark --model llama3 --dataset wikitext-2
wsctl run vision --pipeline meta-vision
5

Step 5: Use the MetaVision API for Vision Tasks

MetaVision exposes REST endpoints for image detection, segmentation, and captioning. You can test these endpoints by sending an image file via multipart/form-data.

curl -X POST http://localhost:8080/api/meta-vision/detect \
  -H "Content-Type: multipart/form-data" \
  -F "image=@/path/to/image.png"

💡 Pro Tips

Pro Tip: Run `docker compose logs -f` to watch real‑time logs and debug container startup issues.
Pro Tip: Use the `wsctl config edit` command to update model catalog entries without restarting the stack.
Pro Tip: If you need to add a new model, push the Docker image to a registry and reference it in the catalog JSON; the hub will pull it automatically.
Pro Tip: Enable NATS monitoring by visiting `http://localhost:8222` to inspect subjects, queues, and message traffic.
Pro Tip: For production, run the inference engine with gVisor (`docker run --runtime=gvisor`) to enforce zero‑trust isolation.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Containers may take longer than expected to become healthy; wait until `docker compose ps` shows status `healthy` before running `wsctl` commands.
Watch Out: Pitfall 2: Docker Compose may fail if the host does not have enough memory or swap; increase resources or use `--scale` to limit heavy workloads.
Watch Out: Pitfall 3: The health endpoint uses port 8080 by default; if that port is already in use, modify `docker-compose.yml` to map a different host port.
Watch Out: Pitfall 4: gVisor requires the `--runtime=gvisor` flag; failing to enable it may expose the host to unsafe code execution.
Watch Out: Pitfall 5: The MetaVision API expects images in JPEG/PNG; sending unsupported formats will result in a 415 Unsupported Media Type error.

❓ Frequently Asked Questions

How do I update the model used by `wsctl`?

Edit the `onecli.yaml` (or the catalog JSON) to change the `model` and `image` fields for the desired model, then restart the Docker stack with `docker compose down && docker compose up -d` to apply the changes.

Can I add my own vision model to MetaVision?

Yes. Place your model’s Docker image in the registry, add its metadata to the MetaVision plugin registry, and expose the required REST endpoints (`/detect`, `/segment`, `/caption`).

What should I do if the `docker compose up` command fails due to insufficient resources?

Increase your Docker Desktop memory allocation (e.g., to 8 GB), or start only the core services with `docker compose up -d --profile core` and add others incrementally.

How can I monitor the NATS message bus in real time?

Open the NATS Web UI at `http://localhost:8222` (default) and view the subjects, queues, and message rates to troubleshoot communication between services.

What is the purpose of the `wsctl benchmark` command?

It pulls a standardized dataset from the catalog, spins up a temporary container for the selected model, streams the data via the NATS bus, and aggregates latency, FLOPs, and token‑level accuracy in real time.
