Daedalus CLI

This guide walks you through using Daedalus CLI to turn a plain‑English specification into a fully scaffolded TypeScript helper, a test suite, and an automated pull request. You’ll see how Daedalus spins up a secure sandbox, generates code, runs tests, and handles the Git workflow without manual commands.

🎯 Key Takeaways

  • 1Daedalus lets you describe a feature in natural language and instantly generates the corresponding source and test files.
  • 2It automatically creates a sandboxed MCP filesystem server to keep the generation environment isolated and reproducible.
  • 3The tool builds a dependency graph, ensuring the new function is exported and correctly imported in tests.
  • 4Test‑Driven Development is enforced from the start – Daedalus writes the `describe` block before the implementation.
  • 5Git operations (branch, commit, PR, merge) are performed automatically, turning a spec into a merged change.
  • 6A high‑level delivery status view shows goal tracking, relationship mapping, and verification checks.
  • 7All of this can be driven from a single terminal session with a handful of Daedalus commands.

📋 Prerequisites

  • Node.js (>=20) and npm installed globally
  • Node.js (>=18) with npm for running the generated TypeScript tests
  • Git configured with access to the target repository
  • A fresh or existing TypeScript project (e.g., `npm init -y && npm i --save-dev jest @types/jest ts-node`)

📝 Step-by-Step Guide

1

Step 1: Install Daedalus CLI

Install Daedalus CLI globally from npm using Node.js (>=20). You can also run it directly via npx. Verify the installation by printing the version.

npm install -g daedalus-cli
# Verify installation
 daedalus version
2

Step 2: Initialise a Daedalus‑enabled project

Navigate to your TypeScript project root and run `daedalus init`. This creates the hidden Daedalus configuration files (e.g., `CLAUDE.md`) and starts a secure MCP filesystem server that sandbox‑isolates all subsequent generation steps.

cd my-ts-project
 daedalus init
# Expected output
[MCP:filesystem] stderr: Secure MCP Filesystem Server running on stdio
3

Step 3: Define the feature with a natural‑language spec

Use the `/spec` command to tell Daedalus what you want. The spec is written in plain English and Daedalus will parse it, ask clarification questions, and then generate the implementation and its test file.

daedalus /spec "Add a helper function to validate version string format and export it in version.ts"
# Daedalus output (truncated)
Fleshing out spec for: "Add a helper function to validate version string format and export it in version.ts"
Gathering requirements...
--- Clarification Questions ---
1. What exact version string pattern should the validator accept?
4

Step 4: Review the automatically generated test file

Daedalus creates `src/version.test.ts` with a full Jest suite. Open the file to verify the positive and negative cases. The test imports the yet‑to‑be‑implemented function `isValidSemver` from `src/version.ts`.

cat src/version.test.ts

import { isValidSemver } from "./version";

describe('isValidSemver', () => {
  const valid = ["0.0.0", "1.0.0", "12.34.56", "1.93.0-canary", "2.0.1-beta.2", "123.456.789"];
  test.each(valid)('accepts %s', (v) => {
    expect(isValidSemver(v)).toBe(true);
  });

  const invalid = ["2", "4", "0.1", "1.02.3", "01.2.3", "1.2.03", "e1.2.2", "-beta"];
  test.each(invalid)('rejects %s', (v) => {
    expect(isValidSemver(v)).toBe(false);
  });
});
5

Step 5: Let Daedalus implement the function and create a PR

After the test file exists, Daedalus automatically writes `src/version.ts` with the `isValidSemver` implementation, runs the test suite, and, once all checks pass, opens a new Git branch, commits the changes, and opens a pull request. No manual Git commands are required.

daedalus run
# Daedalus output (simplified)
> Creating branch daedalus-issue-15
> Adding commits
> Opening PR #15

# Verify PR on GitHub (optional)
open https://github.com/your/repo/pull/15

💡 Pro Tips

Pro Tip: Run `daedalus status` at any point to see the current goal, relationship graph, and remaining checkpoints.
Pro Tip: If Daedalus asks clarification questions, answer them directly in the terminal; the answers are stored in the project rule file for future specs.
Pro Tip: Use the `--dry-run` flag (`daedalus /spec ... --dry-run`) to preview generated files without writing them to disk.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Forgetting to initialise the project first – Daedalus will fail to locate `CLAUDE.md` and cannot load project rules.
Watch Out: Pitfall 2: Using a non‑standard version string pattern – Daedalus will ask for clarification; providing ambiguous patterns can cause incorrect code generation.

❓ Frequently Asked Questions

How does Daedalus understand natural‑language specifications?

Daedalus parses the spec using its built‑in language model (Claude) and then asks clarification questions to disambiguate requirements before generating code.

Can I customize the generated function after Daedalus creates it?

Yes. The generated file is a regular TypeScript module; you can edit the implementation or add additional logic, then re‑run `daedalus run` to update the PR.

What if I want to disable the automatic PR creation?

Use the `--no-pr` flag with the `daedalus run` command. Daedalus will still generate files and commit them locally, but it will not open a pull request.

Which programming languages are currently supported by Daedalus?

Daedalus currently supports Go, TypeScript/JavaScript, Python, and Rust. The language is inferred from the project’s existing file extensions.

How can I debug a generation step that failed?

Run `daedalus log --tail` to view the detailed MCP server logs, and you can also inspect the generated files directly before committing.
