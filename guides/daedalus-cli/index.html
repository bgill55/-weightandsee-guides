Daedalus CLI

This guide walks you through using the Daedalus CLI to create a new feature spec, generate a Jest test scaffold, run the tests, and automatically open a pull request that updates the changelog and version file. By the end you’ll have a fully‑tested commit ready for review.

By Weight and See July 30, 2026 5 Steps

🎯 Key Takeaways

  • 1Daedalus CLI can turn a spec description into a ready‑to‑edit test file.
  • 2The generated tests use Jest as the default test runner.
  • 3Running the CLI after tests pass automatically creates a PR with two commits – one for the spec metadata and one for the test file.
  • 4Release notes and version bumps are written to CHANGELOG.md and version.ts automatically.
  • 5You can customize the test template via the CLI config and amend commit messages before pushing.

📋 Prerequisites

  • Go (>=1.20) installed to build or install the Daedalus binary.
  • Node.js (>=18) with npm installed for the Jest test suite.
  • Git configured with access to the target repository.

📝 Step-by-Step Guide

1

Step 1: Install the Daedalus CLI

Download the latest Daedalus binary or install it via Go. If you have Go installed, run the go install command which fetches the latest release and places the executable in your $GOPATH/bin. Verify the installation by checking the version.

go install github.com/bgill55/daedalus@latest

# Verify installation
 daedalus --version
2

Step 2: Create a spec that generates a test file

Use the `/spec` command to describe the new feature. Daedalus parses the description, asks clarification questions, and then creates a new test file under `src/`. The command automatically splits long specs into paged output for readability.

daedalus /spec "Add a helper function to validate version string format and export it in version.ts"

3

Step 3: Edit the generated Jest test skeleton

Open the newly created `src/version.test.ts`. The file contains a `describe` block with placeholders for positive and negative test cases. Fill in the assertions using Jest’s `expect` API. The scaffold already imports `isValidSemver` from `version.ts`.

import { isValidSemver } from './version';

describe('isValidSemver', () => {
  const valid = ['0.0.0', '1.0.0', '12.34.56', '1.93.0-canary', '2.0.1-beta.2'];
  test.each(valid)('accepts %s', (v) => {
    expect(isValidSemver(v)).toBe(true);
  });

  const invalid = ['2', '4', '1.02.3', '01.2.3', '1.2.03', 'e1.2.2'];
  test.each(invalid)('rejects %s', (v) => {
    expect(isValidSemver(v)).toBe(false);
  });
});
4

Step 4: Run the test suite and ensure it passes

Execute the Jest tests via npm (or npx) to verify the implementation. If the tests fail, edit `src/version.ts` until all cases pass. The CLI can also run the tests directly with a shortcut command.

npm install --save-dev jest

# Run tests
npm test

# Or using Daedalus shortcut (if configured)
 daedalus test
5

Step 5: Commit, push, and let Daedalus create a pull request

After the tests succeed, commit the changes. Daedalus will automatically create two commits – one for the spec metadata and one for the test file – and open a PR titled with the spec reference. The PR also updates `CHANGELOG.md` and bumps the version in `version.ts`. If you need to tweak commit messages, use `git commit --amend` before pushing. Finally, push the branch; Daedalus will handle the PR creation.

git checkout -b daedalus-issue-15
git add src/version.test.ts src/version.ts
git commit -m "spec: Add helper function to validate version string"
# Daedalus adds a second commit automatically for the test scaffold

git push origin daedalus-issue-15

# Daedalus creates the PR
 daedalus pr

# Verify PR on GitHub – it will include CHANGELOG.md and version bump

💡 Pro Tips

Pro Tip: Use the `--config` flag to point Daedalus at a custom config file where you can override the Jest template.
Pro Tip: Run `daedalus status` after each step to see which MCP tools are available and whether root privileges are needed.
Pro Tip: If you see binary garbage in the terminal (e.g., compiled WASM output), pipe the command to a file: `daedalus build > module.wasm`.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Forgetting to install Jest locally – the generated test file will not run. Always run `npm install --save-dev jest` before executing tests.
Watch Out: Pitfall 2: Running Daedalus without root privileges can cause the MCP filesystem warning. The CLI will fall back to allowed directories, but some commands may fail if they require root access.
Watch Out: Pitfall 3: Assuming the spec automatically updates the version file – it only does so after the PR is merged. Make sure to merge the PR before expecting a new version in `version.ts`.

❓ Frequently Asked Questions

Can I customize the generated Jest test template?

Yes. Create a `daedalus.config.json` file in the repo root and set the `testTemplate` field to point at a custom template file. Daedalus will use that template for future `/spec` commands.

What does the STDERR line about MCP Roots mean?

It indicates that the Daedalus client does not have root privileges, so the MCP filesystem falls back to a limited set of directories defined by the server’s arguments. This is normal for non‑privileged users.

How does Daedalus decide what goes into each commit?

The first commit contains the spec metadata (title, description, rule changes). The second commit adds the generated test file and any auxiliary files (e.g., CHANGELOG entry). You can amend the commit messages before pushing if needed.

Why do I sometimes see garbled symbols in the terminal output?

Those symbols represent raw binary data (e.g., a compiled WASM module) being printed to stdout. For practical use, redirect the output to a file instead of displaying it directly.

Is there a one‑click command to run the generated tests and report back to the spec?

After the test file is created, you can use `daedalus test` which runs `npm test` under the hood, captures the results, and updates the spec status in the CLI output.
