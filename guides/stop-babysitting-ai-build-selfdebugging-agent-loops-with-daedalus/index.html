Stop Babysitting AI: Build Self‑Debugging Agent Loops with Daedalus

This guide walks you through setting up Daedalus, a local‑first terminal AI assistant that implements Loop Engineering. You’ll install a local LLM (Ollama or LM Studio), clone the Daedalus repository, configure it to use the model, and run the interactive TUI so the AI can draft code, automatically run compile checks, feed errors back to itself, and roll back failed patches.

🎯 Key Takeaways

  • 1Loop Engineering automates the draft‑verify‑feedback cycle so you no longer have to manually copy stack traces into the LLM.
  • 2Daedalus ships with a built‑in TUI dashboard that shows CPU/memory usage, model overrides, and a file‑tree for dynamic prompt context.
  • 3Self‑debugging works by piping compiler tools (e.g., `tsc --noEmit`, `cargo check`) into the model’s prompt, enabling automatic error‑aware revisions.
  • 4If the AI exhausts its turn budget, Daedalus can roll back to the last known‑good patch using its SQLite session database.
  • 5All of this runs locally—no cloud clusters required—by leveraging Ollama or LM Studio for model inference.

📋 Prerequisites

  • A recent Linux/macOS/Windows terminal with Git, Node.js (>=18) or Rust (>=1.70) installed (depending on Daedalus build system).
  • A local LLM runtime such as Ollama (https://ollama.com) or LM Studio (https://lmstudio.ai).
  • Basic familiarity with CLI navigation and editing source code.

📝 Step-by-Step Guide

1

Step 1: Install a local LLM and pull a model

Daedalus relies on a locally‑hosted LLM. Install Ollama (or LM Studio) and pull a code‑capable model such as `gemma2:2b-code`. Verify the model runs by issuing a simple prompt. For Ollama: ```bash # Install Ollama (macOS example) brew install ollama # Start the Ollama daemon ollama serve & # Pull a code‑oriented model ollama pull gemma2:2b-code # Test the model ollama run gemma2:2b-code "Write a one‑line Python hello world" ```

ollama pull gemma2:2b-code
ollama run gemma2:2b-code "Write a function that returns the factorial of n"
2

Step 2: Clone and install Daedalus

Get the source code, install its dependencies, and build the binary. Daedalus is written in Rust, so we’ll use Cargo for the build. ```bash # Clone the repo git clone https://github.com/daedalus-ai/daedalus.git cd daedalus # Install Rust toolchain if not present curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh # Build the executable cargo build --release # Optionally add the binary to PATH sudo cp target/release/daedalus /usr/local/bin/ ```

git clone https://github.com/daedalus-ai/daedalus.git
cd daedalus
cargo build --release
3

Step 3: Configure Daedalus to use the local model

Create a `daedalus.toml` configuration file in `~/.config/daedalus/`. Point the `model` field to the Ollama endpoint and specify the model name. You can also set the maximum turn budget and the compiler command for your language. ```toml # ~/.config/daedalus/daedalus.toml [model] endpoint = "http://localhost:11434/api/generate" name = "gemma2:2b-code" [loop] max_turns = 5 [verify] # For TypeScript projects command = "tsc --noEmit" # For Rust projects (uncomment if needed) # command = "cargo check" ```

[model]
endpoint = "http://localhost:11434/api/generate"
name = "gemma2:2b-code"
4

Step 4: Launch the interactive TUI dashboard

Start Daedalus in TUI mode. The dashboard shows a side‑by‑side view of the code editor, CPU/memory meters, and a file‑tree. Use the `c` key to open a new coding task, type a brief natural‑language request (e.g., “Add a Jest test for the `sum` function”), and hit **Enter**. ```bash daedalus --tui ``` The assistant will draft a patch, run the verification command (`tsc --noEmit`), and, if it fails, automatically feed the compiler error back into the model for a corrected patch.

daedalus --tui
5

Step 5: Observe the self‑debugging loop and rollback if needed

Watch the loop in action: 1. **Draft** – Daedalus generates a code change. 2. **Verify** – The configured compiler runs; any error output is captured. 3. **Feedback** – Errors are appended to the model’s prompt, prompting a revision. 4. **Rollback** – If the model exceeds its turn budget without a successful compile, Daedalus queries its SQLite session DB, restores the previous patch, and notifies you. You can inspect the session history with `daedalus --history` or manually open the SQLite DB at `~/.local/share/daedalus/session.db`. ```bash # View recent patches daedalus --history # Open the SQLite DB (requires sqlite3 CLI) sqlite3 ~/.local/share/daedalus/session.db "SELECT * FROM patches ORDER BY timestamp DESC LIMIT 5;" ```

daedalus --history

💡 Pro Tips

Pro Tip: Pin a specific model version in `daedalus.toml` (e.g., `gemma2:2b-code@v1.3`) to avoid unexpected behavior after remote updates.
Pro Tip: If you work with multiple languages, create separate `[verify]` sections (e.g., `verify_ts`, `verify_rust`) and switch them via `daedalus --profile rust`.
Pro Tip: Enable `log_level = "debug"` in the config to get a verbose view of the prompt‑feedback cycle; this helps tune prompt engineering.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Forgetting to start the Ollama daemon before launching Daedalus – the model endpoint will be unreachable and Daedalus will time out.
Watch Out: Pitfall 2: Using a compiler command that emits files (e.g., `tsc` without `--noEmit`) – this can clutter the workspace with unwanted build artifacts during the loop.
Watch Out: Pitfall 3: Setting `max_turns` too low – the agent may abort before it can resolve a complex error, leading to premature rollbacks.

❓ Frequently Asked Questions

Can Daedalus work with other LLM backends besides Ollama?

Yes. Daedalus only requires an HTTP `/generate` endpoint that follows the OpenAI‑compatible schema. You can point `model.endpoint` to an LM Studio server, a local vLLM instance, or any self‑hosted inference service.

How does Daedalus decide when to rollback a patch?

If the agent exhausts its `max_turns` without producing a compile‑passing patch, Daedalus reads the last successful patch from its SQLite `patches` table and restores the workspace to that state, then reports the rollback in the TUI.

Is it safe to run Daedalus on a production codebase?

Daedalus is designed for iterative development. It writes patches to a temporary worktree by default and only applies them to the real project after a successful verification step. For production, keep a Git branch or backup and review each patch before merging.

Can I customize the verification command for other languages?

Yes. Add a `[verify]` section in `daedalus.toml` with a `command` field that runs your language’s linter or compiler (e.g., `mypy`, `golangci-lint`, `javac`). Daedalus will pipe the command’s stdout/stderr back to the model.

What does the turn budget control?

The turn budget limits how many prompt‑response cycles the model can take for a single debugging session. Setting it lower prevents endless loops, while a higher budget gives the model more chances to self‑repair before Daedalus rolls back.
