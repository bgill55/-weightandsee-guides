Step 2: Enable Prompt Shielding via the CLI (quick test)

OpenAI ships a convenient CLI wrapper around the SDK. Use the `openai chat` command with `--model cyber` and `--shield true` to send a prompt. The CLI will automatically return a 403 error if the shield blocks the input, letting you verify the guardrail without writing code first.

openai chat --model cyber --shield true --prompt "schedule gym session"

Step 3: Implement a Safe‑Call Wrapper in Python

Wrap the chat call in a helper function that checks the response status. If the shield blocks the prompt (HTTP 403), raise a `PermissionError` so your application can log or remediate the issue. This pattern replaces an implicit trust model with an explicit safety gate.

from openai import OpenAI

client = OpenAI()

def safe_call(prompt: str) -> str:
    """Send a prompt to the Cyber model with shielding enabled.
    Raises PermissionError if the prompt is blocked.
    """
    response = client.chat.create(model="cyber", shield=True, prompt=prompt)
    if response.status_code == 403:
        raise PermissionError("Prompt blocked by shield")
    return response.content

# Example usage
try:
    answer = safe_call("schedule gym session")
    print(answer)
except PermissionError as e:
    print(e)

💡 Pro Tips

Pro Tip: Run the shielded calls asynchronously (`await client.chat.create(...)`) to hide the extra 5 ms latency behind other I/O.
Pro Tip: Log every 403 response with the original prompt and a timestamp; this creates an audit trail useful for security reviews.
Pro Tip: Combine prompt shielding with traditional input validation (e.g., whitelist allowed commands) for defense‑in‑depth.
Pro Tip: Periodically retrain or update the classifier with new injection patterns to keep the false‑negative rate near zero.

⚠️ Common Pitfalls

Watch Out: Pitfall 1: Forgetting to pass `shield=True` – the request will bypass the guardrail and re‑expose the original vulnerability.
Watch Out: Pitfall 2: Treating a 403 error as a generic network failure – you must explicitly catch it to distinguish a blocked prompt from other API errors.
Watch Out: Pitfall 3: Using an overly aggressive classifier that raises false positives, which can cause legitimate agent actions to be dropped.
Watch Out: Pitfall 4: Adding heavy preprocessing logic that negates the low‑latency benefit of the Cyber model.

❓ Frequently Asked Questions

What exactly does the `--shield true` flag do?

`--shield true` activates a pre‑processing classifier that scans the incoming prompt for known command‑injection patterns. If a match is found, the request is rejected with a 403 error before any model inference occurs.

Will enabling prompt shielding noticeably increase inference latency?

No. The classifier processes roughly 150 k tokens per second on a single RTX 4090, adding under 5 ms of latency, which is negligible for most real‑time autonomous‑agent workloads.

How should my application handle a 403 response from the SDK?

Catch the 403 status code, log the original prompt for security review, and optionally retry with a sanitized version or fallback logic. Treat it as a deliberate safety block rather than a generic error.

Can I use the same shielding approach with other OpenAI models (e.g., GPT‑4)?

The `shield` flag is currently only available on the Cyber model. For other models you must implement your own validation layer or use a custom classifier before sending the request.

Is the shielding logic open‑source? Can I adapt it for my own models?

OpenAI has not open‑sourced the exact classifier, but the same principle can be replicated using lightweight text‑classification models (e.g., DistilBERT) trained on a dataset of injection vs. benign prompts, as demonstrated with Llama 4 in the optional step.
